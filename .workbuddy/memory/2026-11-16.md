## distrobox 容器诊断（精确到根因）
- 容器确实存在：`roverx1-dev`，镜像 `docker.io/library/ubuntu:22.04`，2026-10-11 创建，rootless 存储在 `~/.local/share/containers/storage`。
- 本会话 userns 映射只有 `0→1000`（`/proc/self/uid_map` 与 `gid_map` 均单行），因此：属主 `nobody`(65534) 的文件既读写不了也 chown 不了（EPERM）。
- 三重阻塞：① podman 以 euid=0 走 rootful 路径 → `/var/lib/containers/storage/libpod` 属 nobody 不可写；② `/run/libpod`、`/run/lock` 属 nobody 不可创建；③ 容器可写层 `overlay/332e94bd…` 属 nobody 700 → 即使手动 chroot 也读不到层。
- 结论：**当前沙箱身份无法进入该容器**，构建/测试必须在宿主终端由用户执行。不是 distrobox 缺失。

## 理想 ROS2 包结构设计（本次结论）
- 分层按依赖方向切，不按名词堆目录：`interfaces ← core ← {perception, control, voice} ← bringup`，`tools` 平级只依赖 core。
- 硬约束：core 不 import rclpy/cv2（保证离线毫秒级回归）；interfaces 只依赖 std_msgs；bringup 无代码只有 launch/config。
- 检测器作为 composable node 进同一 container（共享 camera2 解码一次），相机驱动独立进程（故障域隔离）。
- 现结构反模式：单包 find_packages 吞掉 9 个顶层模块（`import config` 安装后冲突）、`ros2/` 子目录放接口包需 `--base-paths` 兜底、legacy dataclass 与 ROS msg 双轨须有唯一转换入口。
- 落地顺序：① interfaces+core（不动运行逻辑，先让 core 单测脱离 ROS 跑通）② perception 组件化 ③ control/voice/bringup。
